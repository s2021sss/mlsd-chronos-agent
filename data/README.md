# Данные

Это справочник для работы с данными: где лежат файлы, как их собрать, как устроен каждый элемент набора и по каким правилам он размечен. Зачем нужны эти данные, откуда они взялись, как проверен эталон и каких данных не хватает, описано в [дизайн-документе, этап 1](../docs/ml_system_design_doc.md#этап-1-подготовка-данных). Выводы EDA с графиками собраны в [reports/eda.md](../reports/eda.md).

```text
data/
  raw/          # скачанные внешние датасеты, в git не попадают
  source/       # исходники наборов и эталоны
  interim/      # большие наборы, собираются скриптом, в git не попадают
  processed/    # наборы в схеме проекта, небольшие, хранятся в git
```

Сборка и проверка всех наборов: `uv run python scripts/build_datasets.py`. Сборка также делит примеры с полным эталоном на `dev` и `test` (поле `split`).

Синтетика генерируется командой `uv run python scripts/generate_synthetic.py` (с `--dry-run` только оценка числа вызовов и токенов, с `--wave 2` вторая волна, с `--max-calls 0` пересборка только из кэша, без ключа и без обращения к API).
Скрипт работает с любым провайдером, у которого есть OpenAI-совместимый API: адрес, ключ и модель задаются переменными `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL` в окружении или в `.env` (пример в `.env.example`). Модель, которой сгенерирован пример, записана в его `meta.model`. Ответы модели кэшируются в `interim/generation/`, промпт лежит в `scripts/prompts/synthetic_system.txt`.

## Исходный вид наборов и приведение к общей схеме

Наборы изначально имели разную структуру, поэтому почти все требовали предварительной обработки. Их приводят к единой схеме, описанной ниже, чтобы сравнивать одинаковые поля: исход, операцию, тип, время и цель каждого дела. Это позволяет использовать общий код оценки для всех наборов, проверять примеры через `scripts/dataset_schema.py` и формировать срезы по единым тегам.

| Набор | Исходный вид | Что делает сборка | Почему так |
| --- | --- | --- | --- |
| MASSIVE | JSONL с данными Amazon на 51 языке. Каждая фраза содержит интент (`calendar_set`, `calendar_query`, `calendar_remove`, `alarm_set` и другие), а слоты размечены прямо в тексте (`разбуди меня в [time : пять утра]`). Также доступны оценки трёх разметчиков. | Оставляет только домены `calendar` и `alarm`. Исход определяется по интенту: `query` соответствует `answer`, `set` без даты и времени соответствует `clarify`, остальные случаи относятся к `plan`. Операция определяется по действию: `set` это `create`, `remove` это `delete`, а «перенеси» это `update`. Для будильников и напоминаний указывается тип `reminder`, для остальных случаев `event`. Название берётся из слота `event_name`, а согласие разметчиков сохраняется в `meta`. | Это единственный набор с реальными пользовательскими фразами, но в нём нет времени отправки сообщения, поэтому восстановить точное время события нельзя. Эталон считается ненадёжным (`label_status: weak`), поэтому набор используется для EDA и анализа распределения по исходам и типам, но не для расчёта Plan match. Из-за большого размера данные скачиваются скриптом, хранятся в `interim/` и не добавляются в git. |
| Seed-набор | YAML с 32 примерами для старой функции `extract_intent`. Для каждого случая указаны текст и частичные ожидания: действие, подстрока названия, час, день недели и длительность с допуском 15 минут. | Полный эталон в схеме проекта лежит в `seed_gold.yaml`. Скрипт сверяет его с исходными ожиданиями. Все расхождения должны быть объяснены в поле `changed_from_seed`. Таких случаев два. | Частичной разметки недостаточно для расчёта Plan match. Сверка с исходными ожиданиями помогает сохранить смысл примеров при переходе к полной разметке. |
| Имитация пользователя | YAML, в котором примеры сразу представлены в схеме проекта. Общие значения `now` и `timezone` вынесены в `defaults`. | Подставляет значения по умолчанию и сохраняет примеры в JSONL. | YAML удобен для ручного создания и редактирования примеров, а JSONL позволяет использовать единый формат для всех наборов. |
| Синтетика, обе волны | Карточки, которые генерирует код. Для каждой задаются эталонный план, календарь и фразы с датами. Модель возвращает JSON с текстом сообщения и фрагментом текста для каждого дела. | Генератор проверяет ответы модели и сохраняет принятые примеры в `source/` уже в схеме проекта. При сборке к ним добавляется только поле `split`. | Эталонный план формируется кодом до генерации текста, поэтому он известен заранее и не требует ручной разметки. |
| Вторая разметка | JSONL с исходом и планом второй разметки для 50 случайно выбранных сообщений. Фрагменты исходного текста не сохраняются. | Не попадает в `processed/` и используется только в ноутбуке EDA для расчёта согласия между разметками. | Это не отдельный набор данных, а дополнительная проверка качества эталонной разметки. |


## Схема примера

Каждая строка JSONL содержит один пример со следующими полями:

| Поле | Значение |
| --- | --- |
| `id`, `source`, `text` | Идентификатор примера, источник (`seed_llm`, `imitated_user`, `synthetic_llm`, `massive`) и текст сообщения |
| `label_status` | Статус эталона: `full` означает, что разметка полная и проверена, `weak` – что она получена автоматически и не содержит информации о времени |
| `now`, `timezone` | Время отправки сообщения и часовой пояс пользователя |
| `outcome` | Исход обработки сообщения: `plan`, `answer`, `clarify` или `unsupported` |
| `items` | Элементы плана, если исход – `plan` |
| `missing` | Недостающая информация, если исход – `clarify` |
| `answer_window` | Интервал, о котором спрашивает пользователь, если исход – `answer` |
| `calendar` | Состояние календаря и задач до обработки сообщения |
| `tags`, `meta` | Метки для расчёта метрик и служебная информация об источнике |

Структура элемента плана соответствует [разделу 2.1 дизайн-документа](../docs/ml_system_design_doc.md#21-постановка-задачи). Она включает поля `op` (`create`, `update`, `delete`, `complete`), `type` (`event`, `task`, `reminder`), `title`, `start`, `end`, `remind`, `target` и `span`.

## Соглашения разметки

Значения по умолчанию взяты из [раздела 1.4 дизайн-документа](../docs/ml_system_design_doc.md#14-предпосылки-решения). Остальные правила определены при подготовке разметки:

- Относительные даты рассчитываются от `now`, а указанный день недели означает ближайший такой день в будущем.
- Для задачи в поле `start` указывается срок в виде даты, а для напоминания – момент уведомления. Поле `end` в обоих случаях не заполняется.
- Поле `remind` заполняется только тогда, когда пользователь явно просит напомнить о встрече.
- При операции `update` указываются итоговые значения `start` и `end`. Для `delete` и `complete` время не указывается.
- `complete` отмечает выполненной задачу из календаря, на которую указывает `target`, и применяется только к типу `task`.
- Если эталон сгенерированного примера пришлось исправить после генерации, исправление записывается в `source/gold_overrides.yaml` с причиной. Сборка применяет его поверх синтетики после деления на dev и test, поэтому split не сдвигается, а генератор и кэш остаются прежними.
- Фраза «до конца недели» трактуется как воскресенье.
- Если запрошенное время конфликтует с существующим событием, в эталоне сохраняется именно запрошенное время, а примеру присваивается тег `conflict`.
- Если пользователь указывает время в прошлом или невозможное время, исходом становится `clarify`.
